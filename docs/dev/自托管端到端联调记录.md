# 自托管端到端联调记录（WebClient → 自托管信令 → Windows 被控端）

> 记录日期：2026-10-15
> 目的：在**没有本 fork Windows 产物**的前提下，先证明产品链路真的能跑通，
> 再把结论固化成可复现的操作手册。
> 结论一句话：**画面、鼠标、键盘三条路全部打通**，被控端是 Parallels
> Windows 11 ARM64 虚拟机里跑的上游 QuickDesk v4.2.0.0。

## 3. 实际链路

1. 控制端 `POST /v1/devices/:id/access-code:verify` 换取一次性 `signal_token`；
2. 打开 `remote.html?server=&device=&st=&codec=AV1`，WebSocket 连 `/v1/realtime/signal`，
   读到 `auth_ok` 后发起 `session-initiate`；
3. 走 SPAKE2 认证（access_code 作为共享密钥，经 sessionStorage 交接，不进 URL）；
4. WebRTC 建立后，视频经 `remoteVideo` 解码；控制事件走 `event` DataChannel，
   光标形状/能力协商走 `control` / `video_stats:*` / `actions`；
5. 被控端侧由 remoting 的 `MouseInputFilter` / `HostControlDispatcher` 落地成真实输入。

## 4. 两个必须知道的坑

### 4.1 设了 `ALLOWED_ORIGINS` 就必须同时设 `API_KEY`

`APIKeyAuth.Required()` 是「**二选一**」语义：`X-API-Key` 或 Origin 白名单命中其一即放行。
但只要 `API_KEY` 或 `ALLOWED_ORIGINS` 任一非空，这道闸门就**开启**。

- 只配 `ALLOWED_ORIGINS`（为了浏览器跨域 CORS）→ 原生被控端不带 Origin，
  所有 `signal-tokens` / `heartbeat` / `preset` 请求全部 `403 FORBIDDEN`，设备永远不上线。
- 只配 `API_KEY` → 浏览器拿不到 CORS 头，前端全部请求被浏览器拦掉。

所以自托管要同时配：服务端 `API_KEY=<secret>` + `ALLOWED_ORIGINS=<前端来源>`，
并在被控端 `appconfig.db` 里写 `apiKey=<同一个 secret>`（Qt 客户端会把它作为
`X-API-Key` 注入到 host/客户端的 HTTP 请求）。本次就是踩了这个坑后才上线的。

> 另一条更省事的路子：让前端与 API **同源**（nginx 反代，仓库里已有
> `setup-nginx.sh`），这样 `ALLOWED_ORIGINS` 留空、闸门关闭，原生客户端与浏览器
> 都不需要额外配置。两条路选一条即可，不要只配一半。

### 4.2 被控端配置路径不含组织名，且 host 会自己缓存服务器地址

- 实际路径是 `%APPDATA%\QuickDesk\db\appconfig.db`（**没有** `QuickCoder\` 这一段），
  键名是 `signalingServerUrl` / `apiKey`；同一个目录下还有 remoting 自己的
  `host.conf`（含 `device_id`、`device_secret_blob_b64`、`signaling_server_url`）。
- 一旦 host 用某个地址 provisioning 成功，它会把该地址写进 `host.conf` 并复用
  `device_id`。**换服务器必须先删掉/改名 `host.conf`**，否则会用旧服务器上已注册的
  device_id 去新服务器认证，表现为一直重连失败。
- Windows 服务方式（`quickdesk_host.exe --type=service`，LocalSystem，
  `--config-dir=...\systemprofile\AppData\Roaming\QuickDesk`）走的是另一套配置目录，
  且不经过 `ProcessManager::startProcess()`，需要单独准备配置。

### 4.3 防火墙弹窗会吃掉键盘输入

首次连接时 Windows 会弹「安全中心」防火墙同意框。它以更高完整性运行，
**用户态 UI Automation 都枚举不到**，但会抢走焦点：鼠标仍然生效（我们就是用它点的
「允许」），键盘事件则全部落在弹窗上，表现为「打字没反应」。
预置 `netsh advfirewall firewall add rule ... program=quickdesk_host.exe` 可以避免复现。

## 5. 复现步骤

```bash
# 依赖：Docker（PostgreSQL + Redis）
docker run -d --name qd-postgres -p 5432:5432 \
  -e POSTGRES_USER=quickdesk -e POSTGRES_PASSWORD=quickdesk123 \
  -e POSTGRES_DB=quickdesk_signaling postgres:15
docker run -d --name qd-redis -p 6379:6379 redis:7 \
  redis-server --appendonly yes --notify-keyspace-events Ex

# 信令服务（.env 见 SignalingServer/.env.example，本次关键项）
#   API_KEY=qd-local-dev-key
#   ALLOWED_ORIGINS=http://127.0.0.1:5173,http://localhost:5173
cd SignalingServer && go run ./cmd/signaling

# 控制端静态站点 + 端到端脚本
cd WebClient && npm run build && python3 -m http.server 5173 --bind 127.0.0.1 --directory dist
cd ../../scripts/e2e && QD_TOKEN=<token> QD_DEVICE=<device_id> node remote-smoke.mjs
```

被控端侧的准备（安装、写配置、输入靶子）见 `scripts/e2e/README.md`。

## 9. 录出真文件了：控制端录制闭环

设计文档里一期选的是「控制端录制」。Web 控制端这条路径不需要动 remoting、
也不需要重编 Chromium，所以先把它做完：

1. `WebClient/js/remote-main.js` 新增录制能力：直接取 `#remoteVideo.srcObject`
   （远端解码后的 MediaStream）喂给 `MediaRecorder`，优先选 `video/mp4;codecs=avc1`
   （Chrome 126+ 可直接 mux MP4），回退到 WebM/VP9；
2. 停止录制后先 `POST /v1/me/recordings` 建索引行，再
   `POST /v1/me/recordings/:id/artifact` 以 multipart 上传字节；
3. 连接条上加了录制按钮（红点闪烁 = 录制中）；
4. 服务端侧同步补齐：产物落盘（`RECORDING_DIR`，文件名由 `user_id + recording_id`
   派生、白名单扩展名、先写 `.part` 再 rename）、上限 `RECORDING_MAX_UPLOAD_MB`、
   以及**签名播放 URL**（`POST /v1/me/recordings/:id/artifact-ticket` →
   `GET /v1/recordings/:id/artifact?t=...`）。

签名 URL 是必须的：`<video src>`、`window.open`、`<a download>` 都带不上
`Authorization` 头，纯 Bearer 路由在浏览器里必然 401。所以该 GET 特意注册在
API-key 与用户鉴权组之外，靠短时 HMAC 票据（默认 10 分钟、绑定 recording+user）
鉴权，并且**没有**挂任何静态目录。

实测（2026-10-15，被控端为 fork 自建 4.2.1.0）：

| 步骤 | 证据 |
|---|---|
| 录制 | 远端会话中点击录制按钮，7 秒后停止；页面日志出现「开始录制本次会话画面」→「录制结束：7s / 19 KB，正在上传...」→「录像已上传并通过索引登记（id=5，19 KB）」 |
| 落库 | `GET /v1/me/recordings/5` 返回 `status=completed`、`format=mp4`、`size_bytes=19139`、`duration_seconds=7`、`artifact_path=data/recordings/1/rec-5.mp4` |
| 文件真实性 | `ffprobe` 读出 `h264` 视频 `1700x768` + `opus` 音频，`duration=6.98s`，容器为 `mov,mp4` |
| 回放 | WebClient 录像页点「播放」→ 浏览器打开签名 URL → `videoWidth/Height=1700x768`、`duration=6.98`、`currentTime` 2.31s → 4.81s 持续推进；见 `docs/e2e/e2e-recordings-page.png` |
| 鉴权 | 无票据访问 `?t=bogus.sig` → 401；无 Bearer 访问 `/v1/me/.../artifact` → 401；带票据不带任何头 → 200 且字节哈希一致 |
| 管理侧 | 管理员下载同一文件哈希一致，并写出 `recording.download` 审计 |

也就是说：**「录 → 存 → 索引 → 播放」这条链已经跑通并留证**。

仍然没做的：Qt 控制端录制（`QScreenCapture`/`QMediaRecorder` 或共享内存 I420 二次编码），
以及被控端权威录制（需要 fork remoting）。Web 控制端这条路径只录控制者看到的画面，
不产生被控端视角的独立录像。

## 10. Qt 控制端录制（桌面客户端）

第 9 节做完的是 Web 控制端。桌面客户端走的是另一条实现路径，而且**不需要 FFmpeg SDK**：
Qt 6.8 的 `QMediaCaptureSession::setVideoFrameInput()` 可以接收 `QVideoFrame`，于是可以把
`SharedMemoryManager::readVideoFrame()` 读到的远端解码帧（I420，`readVideoFrame` 内部已把
各 plane 拷进自有 buffer，所以不存在与生产者的竞态）直接喂给 Qt Multimedia 的编码器。
这样既不动 remoting，也不引入新的第三方编码依赖。

实现落在 `QuickDesk/src/manager/DeviceRecorder.cpp`：

- 15fps 定时从共享内存取帧 → `QVideoFrameInput::sendVideoFrame()`；
- `QMediaFormat` 选 MPEG4 + H.264，`QMediaRecorder` 输出到临时目录的 mp4；
- 停止后先 `POST /v1/me/recordings` 建索引行，再用 `QHttpMultiPart` 上传到
  `/v1/me/recordings/:id/artifact`，复用 `AuthManager` 的 `X-API-Key` + Bearer 头；
- 上传成功后删除临时文件。

入口在远程窗口左上角的录制按钮（红点闪烁 = 录制中），同时提供 `Ctrl+Shift+R` 快捷键与
`Accessible.name`（后者让 UI 自动化能定位到它，验证脚本就是靠它和快捷键驱动的）。

### 验证结果（fork 自建 4.2.4.0，被控端 = PD Windows 虚拟机）

| 步骤 | 证据 |
|---|---|
| 构建 | `quickdesk-windows.yml` run `38735621240` 成功；产物装进虚拟机后设备 `app_version=4.2.4.0` |
| 录制 | 客户端自连同一台主机（自连只禁用输入、不禁视频），`Ctrl+Shift+R` 起录 12 秒后停止 |
| 日志 | `DeviceRecorder: recording started device=126735214 path=...quickdesk-rec-*.mp4`；随后上传成功、临时文件被删除 |
| 落库 | `GET /v1/me/recordings/7` → `status=completed`、`format=mp4`、`size_bytes=2193967`、`duration_seconds=14`、`session_id=qt-*` |
| 文件真实性 | `ffprobe`：H.264 **1700x768**、**221 帧**、`91/6≈15.2fps`、**duration=14.587s**、1.2 Mbps |
| 回放 | WebClient 录像页点播放 → 签名 URL → `duration=14.587`、`currentTime` 2.46s → 4.96s 持续推进 |

### 验证过程抓到的真实缺陷（已修）

第一版（4.2.3.0）录出来的 mp4 只有 **0.0145 秒**：`QVideoFrame` 的 presentation timestamp
单位是**微秒**，而代码按毫秒写入（`now - startMs`）。结果是 14 秒的画面被压成 14 毫秒。
编译、上传、索引、甚至浏览器播放都"成功"，只有 `ffprobe` 看时长才暴露出来。
修复是改用微秒（`134a81e`，4.2.4.0），并把"时长必须 > 1 秒"写成 `scripts/e2e/playback.mjs`
的断言，避免同类问题再次静默通过。

### 仍然没做的

- 被控端权威录制（需要 fork `quickdesk-remoting` 并升 native-messaging 协议版本）；
- 缩略图、保留期 GC、并发压测（其中保留期 GC 见 §11，缩略图见 §12）；
- 本节的验证是在**同一台虚拟机内自连**完成的（画面是递归镜像），它证明了录制链路，
  但没有替代"Mac 控制 Windows"的跨机验证。

## 11. 录像的生命周期与失败语义

第 9、10 节解决了"能录、能播"，但留下两个会随时间恶化的洞：客户端崩溃会留下永远停在
`recording` 的行；媒体文件只增不减，自托管部署迟早被磁盘撑爆。另外，上传失败时客户端
会把行留在 `completed`——**索引说录像存在，而文件根本不在**。

### 服务端

- `RECORDING_STALE_MINUTES`（默认 240）：超过这个时长的 `recording` 行自动置 `failed`；
- `RECORDING_RETENTION_DAYS`（默认 0 = 永久保留）：过期的媒体文件被删除，但**索引行保留**，
  同时清空 `artifact_path` / `artifact_url` / `size_bytes`（于是前端不再提供播放，产物路由返回 404）；
- `RECORDING_SWEEP_INTERVAL_MINUTES`（默认 30）后台定时跑；管理端也可立即触发：
  `GET /v1/admin/recordings:storage`、`POST /v1/admin/recordings:sweep`（写 `recording.sweep` 审计）。

实测（真实服务 + 真实文件）：

| 操作 | 结果 |
|---|---|
| 造一条 6 小时前卡住的 `recording` 行 + 一条 3 天前带 4096 字节文件的 `completed` 行 | — |
| `POST /v1/admin/recordings:sweep` | `{"stale_marked_failed":1,"artifacts_purged":1,"bytes_freed":4096}` |
| 卡住的行 | `recording` → **`failed`** |
| 过期的行 | 仍是 `completed`，但 `artifact_path`/`artifact_url`/`size_bytes` 已清空，**索引保留** |
| 磁盘 | `rec-900.mp4` 被删除；真实录像 4/5/6/7 一个没动 |
| 清理后的产物路由 | 过期的行取 ticket → **404**；正常行 7 → 200 |
| 用量 | `recordings:storage`：6 个产物 / 56,795,649 字节 → 5 个 / 56,791,553 字节 |

### 客户端失败语义

两个控制端都改成：**先建 `recording` 行 → 上传字节 → 服务端在产物落地时才翻成 `completed`；
上传失败则显式 PATCH 成 `failed` 并清掉本地临时文件**。这样索引永远不会声称一份不存在的录像。

验证用两种确定性失败注入：

| 端 | 注入方式 | 结果 |
|---|---|---|
| Web | Playwright 拦截并中断 `POST .../artifact` | 新行 `failed`、`artifact_url` 为空、`size_bytes=0` |
| Qt | 服务端把 `RECORDING_MAX_UPLOAD_MB` 压到 1（录制约 2MB，必然被拒） | 新行 `failed`、无产物，**被控端临时目录无残留 `quickdesk-rec-*.mp4`** |

失败注入还抓到一个真 bug：Web 端原本写的是 `if (!uploaded.ok) markFailed(...)`，
但 `fetch` 在传输层失败时是**抛异常**而不是返回非 2xx——这条分支永远不会执行，行就被留在
`recording`。修复是把「建行之后的所有失败」统一收敛到 `catch` 里补 PATCH。

恢复上限后重录一次作为回归：新行 `completed`、3,330,663 字节、15 秒、有 `artifact_url`；
`ffprobe` 读出 H.264 2082×1002 / `duration=15.644s`，WebClient 回放 `currentTime` 2.44s → 4.95s。

### 仍然没做的

- 缩略图（见 §12，已补上）；
- 对**已经**失败的行重新上传的服务端入口——客户端的首次上传现在自带退避重试（§12），
  但用户仍然没有"重传这条旧录像"的按钮；
- 并发录制的容量与压测。

## 12. 预览图与上传韧性

§11 之后录像能录、能存、能播、能回收，但列表里每条都只是文字，而且"网络抖一下就
整段丢掉"。这一节补上两件事：**预览图**（`thumbnail_url` + 抓帧 + 上传 + 渲染）和
**上传重试**（只在能修好的错误上重试）。

### 服务端

新增 `/v1/me/recordings/:id/thumbnail` 上传、`GET` 读取、`thumbnail-ticket` 签名 URL，
以及管理端的 `GET /v1/admin/recordings/:id/thumbnail`。设计上沿用产物的存储规则
（文件名由 id 派生、写 `.part` 再改名、无静态目录挂载），但有两点不同：

- **按内容而不是按扩展名判定**：读前 8 字节做 magic 嗅探（JPEG `FF D8 FF`、PNG 八字节
  签名），并且要求声明类型与内容一致，落盘扩展名由内容决定。图片是要被列表内联渲染的，
  只信文件名等于给自己开了一个投递任意字节的口子；
- **上限独立**：`min(2 MiB, RECORDING_MAX_UPLOAD_MB)`。

保留期 GC 一并处理预览图：`ClearArtifact` 同时清空 `thumbnail_path` / `thumbnail_url`，
`SweepOnce` 删除媒体文件与预览文件，只带预览图的孤儿行也会被纳入候选。票据新增 `kind`
字段，播放票据与预览票据互不通用。

实测（真实服务，录像 13 的真实 MP4 抽帧得到 113,058 字节 JPEG）：

| 操作 | 结果 |
|---|---|
| `POST .../thumbnail`（multipart，真实 JPEG） | 200，`thumbnail_path=data/recordings/1/thumb-13.jpg` |
| `GET .../thumbnail`（Bearer） | 200，sha256 与上传文件**逐字节一致** |
| 匿名 `GET /v1/recordings/13/thumbnail?t=...` | 200，sha256 一致（`<img>` 没有 Authorization 可用） |
| 用**播放**票据访问预览路由 / 用**预览**票据访问产物路由 | 两个方向都是 **404**（kind 隔离生效） |
| 文本字节伪装成 `fake.jpg` | **400** `thumbnail bytes do not match an allowed image type` |
| PNG 字节声明为 `.jpg` | **400** `thumbnail content does not match its declared type` |
| PNG 声明为 `.png` | 200，落盘 `thumb-13.png`，原先的 `thumb-13.jpg` 被删除 |
| 裸流上传 `?ext=.jpg` | 200，落回 `thumb-13.jpg` |
| 无票据无凭证 / 伪造票据 | **403** / **401** |
| 造一条 3 天前同时带 mp4 与 jpg 的行 → `POST /v1/admin/recordings:sweep` | `{"artifacts_purged":1,"bytes_freed":4096}`，**两个文件都消失**，索引行保留、四个媒体字段清空 |

### Web 控制端

录制开始时从 `#remoteVideo` 抓首帧（不是停止时抓——那时解码器可能已经拆掉，画布是空的），
缩放到长边 640 后转 JPEG，产物上传成功后再作为**尽力而为**的第二步上传；预览失败只提示，
不会把一条已经存好的录像标成失败。

上传加了退避重试（`[0, 800, 2000, 5000] ms`，共 4 次），并且**只重试传输错误与 5xx/429**：
4xx 是服务端对这份载荷的判断，重放没有意义。

| 注入 | 结果 |
|---|---|
| 连续中断 2 次 `POST .../artifact` + 1 次 `POST .../thumbnail`（`scripts/e2e/record-retry.mjs`） | 日志出现 3 条"上传中断，正在重试"，最终行 `9904` `completed`，`artifact_url` 与 `thumbnail_url` **都有值** |

真实录制（未注入）产出 640×308 JPEG，`file` 识别为 `JPEG image data, baseline`，
列表页截图确认预览图渲染在行首、无预览的行显示占位图标。

### Qt 控制端

`DeviceRecorder` 在第一个有效 `QVideoFrame` 上做一次 `toImage()` → 缩放 640 长边 →
JPEG 存到临时录像文件旁边，随后用与 Web 相同的重试策略上传
（同一套 `postFileWithRetry`，`kMaxUploadAttempts=4`）。临时文件保留到上传成功或重试耗尽，
预览失败只记 warning，不影响已经完成的录像。

### 顺带修掉的两个存储问题

验证过程中发现**删除录像行不会删磁盘文件**：`DELETE /v1/me/recordings/:id` 只删行，媒体和预览图永远留在
`RECORDING_DIR` 里，而保留期清理是**从行出发**的，所以这些孤儿文件再也不会被回收。修法有两层：

1. `Delete` / `DeleteAdmin` 先取出行、再删行、最后删掉它指向的媒体与预览文件（失败只记日志，不影响删除结果）；
2. `SweepOnce` 增加一趟**孤儿回收**：扫描 `<dir>/<user_id>/` 下能解析出录像 id 的文件
   （`rec-<id>.<ext>` / `thumb-<id>.<ext>`），若索引里已经找不到这行、且文件 mtime 超过 1 小时，就删掉。
   `.part` 这类上传临时文件故意**解析不出 id**，因此永远不会被这一趟误删。

实测：建行 → 传产物 + 预览 → `DELETE`，`rec-9909.mp4` 与 `thumb-9909.jpg` 同时消失；
手工放两个 2 小时前的孤儿（`rec-90001.mp4`、`thumb-90001.jpg`）+ 一个新孤儿（`rec-90002.mp4`）+ 一个
`rec-9909.mp4.part`，sweep 返回 `{"artifacts_purged":0,"bytes_freed":0,"orphans_removed":2,...}`，
两个旧孤儿被清、**新文件与 `.part` 都保留**。

顺带修了一个语义漏洞：以前往 `failed` 的行重新上传，字节落库了但状态仍是 `failed`（索引和文件互相矛盾）。
现在产物落地一律把行翻成 `completed`（`README` 里那句"leave failed untouched"只对**之后**到来的失败
PATCH 生效）。实测：往 `failed` 行上传 → `completed`；随后 PATCH `failed` → 仍是 `failed`。

### 并发录制

`scripts/e2e/record-concurrent.mjs` 同时开 N 个浏览器会话录同一个设备（每路独立建行、独立产物、独立预览）：

| 并发数 | 结果 |
|---|---|
| 2 | 两行 `completed`（2,566,293 / 1,915,641 字节），两路都有 `thumbnail_url` |
| 4 | 四行 `completed`（最大 7,153,738 字节），四路都有 `thumbnail_url` |
| 6 | 六行 `completed`，6 张预览图 **sha256 各不相同**，磁盘上 6 个 mp4 + 6 个 jpg |
| 10 | 十行 `completed`（805 KB ~ 7.8 MB），十路都有 `thumbnail_url`，`RESULT=PASS` |

一次 4 路运行出现过一路没上传（那次记录里该会话没有拿到录制状态），重跑 4 路与 6 路均通过；
当前证据支持"单设备 10 路并发控制端录制可用"（每路独立建行、独立产物、独立预览），
但**长时间运行稳定性、带宽上限、以及 10 路以上的表现没有数据**。

### 仍然没做的（截至本节）

- 对**已经**失败的历史行做"重新上传"的服务端入口；
- 被控端权威录制（仍需要 fork `quickdesk-remoting`）；
- 长时间稳定性、带宽上限，以及 10 路以上的并发压测。

## 13. 屏幕墙（DeskHub / Video Wall）

路线图里「屏幕墙」一直是**缺失**项：WebClient 只能一台一台开窗口看。这一节把它补上。

### 做法

砖块就是 `remote.html` 的 iframe，而不是把 Remoting 客户端塞进 Vue 组件里——这样每个砖各自持有
一个独立的 remoting 会话，不动 Remoting 内核，也不需要在 SPA 里重写 WebRTC/解码链路。

每块砖需要自己的**一次性 signal token**，所以屏幕墙把设备页那套流程按设备跑一遍：
`POST /v1/devices/:id/access-code:verify` → `remote.html?device=..&st=..&wall=1`
（access_code 依旧只通过 `sessionStorage` 交接，不进 URL）。

`remote-main.js` 新增**墙模式**（`?wall=1`）：

- **只看不控**：不创建 `MouseHandler` / `KeyboardHandler` / `TouchHandler`；
- 不创建悬浮工具条，并通过 CSS 隐藏砖内的连接条、日志抽屉、统计面板与移动工具条——砖的
  chrome 全部由屏幕墙页面提供（设备名、状态徽标、三个操作按钮）；
- 不做「点击开启声音」覆盖层（墙是监看视图，N 个砖同时弹提示只是噪音）；
- 用 `postMessage` 把 `connecting / connected / live / error` 上报给父页，父页据此显示
  「连接中 / 已连接 / 画面中 / 失败」，而不是靠肉眼猜 iframe 里的内容。

砖块状态除了会话状态，还有两种来自服务端设备列表的情况：**设备离线**与**被控端未登录**，
这两种不建会话，直接显示占位与「重新连接」。

### 实测（真实服务 + Windows 被控端）

`scripts/e2e/wall.mjs`：把在线设备 `256983850` 与离线旧设备 `126735214` 同时放上墙。

| 断言 | 结果 |
|---|---|
| 在线砖徽标 | `画面中`（父页通过 postMessage 收到的状态） |
| iframe 内 `<video>` | `videoWidth=1868`，`currentTime` 0.93s → 3.93s **持续推进** |
| 只看不控 | `mouseHandler=false`、`keyboardHandler=false`、`touchHandler=false` |
| 砖内 chrome | 连接条 `display:none`（且根本没创建悬浮工具条） |
| 离线设备砖 | 无 iframe，占位显示「设备离线」+「重新连接」 |
| 版式 | 侧边栏新增「屏幕墙」；顶部含「墙上 N 台设备 / 每行 / 刷新 / 全部重连 / 添加设备 / 清空屏幕墙」 |

截图：`docs/e2e/e2e-wall.png`。

### 砖内输入开关（默认只看，显式解锁）

监看视图默认不控，但真实运维常常需要在某一块砖上临时操作一下。做法是**解锁而不是常开**：

- 每块砖一个锁按钮（`🔒 解锁输入` / `🔓 锁定输入`），**同一时间只允许一块砖持锁**——解锁第二块会
  自动锁掉第一块，不会出现一次按键同时打进多台机器；
- 解锁是墙页发给砖的 `postMessage`（`quickdesk-wall-control`），砖收到后才创建
  Mouse/Keyboard/Touch 处理器；锁定立刻 `_cleanupInputHandlers()` 并把处理器置空；
- 持锁的砖有明确视觉标记（红色边框 + `输入已解锁` 徽标），避免"看着像在看，其实在控"。

实测（同一台 Windows 被控端 + `guest-input-target.ps1` 输入靶子）：

| 断言 | 结果 |
|---|---|
| 默认（未解锁） | `mouseHandler=false`、`keyboardHandler=false`、`touchHandler=false` |
| 点击解锁 | 徽标变 `输入已解锁`，`mouseHandler=true`、`keyboardHandler=true` |
| 真机按键 | 在砖内键入 `qd-wall-094468`，被控端输入靶子 spool 文件末尾出现 **`qd-wall-094468`** |
| 再点锁定 | 两个处理器重新变回 `false` |

截图：`docs/e2e/e2e-wall-armed.png`（左砖红框持锁、被控端窗口里能看到打进靶子的文本）。

### 单砖放大与轮巡

控制室最常见的两个动作：把一台机器放大看，以及在大屏上轮流看几台。两者都落在墙页本地状态上，
不动会话：

- **放大**：砖头 `⤢` 让该砖横跨整行（`grid-column: 1 / -1`），其它砖留在下方网格，iframe 不重建、
  会话不断；
- **轮巡**：`开始轮巡` 按间隔（5/15/30/60s，默认 15s，存在 localStorage）依次把焦点移到下一台设备，
  停止后焦点停在当前砖；**有砖持锁输入时禁止轮巡**（按钮禁用并提示），避免"正在操作却被轮走"。

实测：放大前砖宽 654px → 放大后 **1320px**（整行），其它砖仍 654px；把轮巡间隔设成 3s 后启动，
焦点从空 → `126735214`，点「停止轮巡」后再等 4.5s 焦点**不再变化**。

截图：`docs/e2e/e2e-wall-focus.png`（在线砖横跨整行放大，工具条出现「开始轮巡」）。

### 仍然没做的

- 墙级音频（多路声音的意义与策略待定，现在是静音）；
- 分页式轮巡（现在是"全部砖都在 DOM 里、只移动焦点"，几十台时需要按页挂载/卸载以省资源）；
- 上游贡献：屏幕墙与 PR #23（录像）改了同一批 WebClient 文件（导航、路由、i18n），
  同时开两个 PR 会在合并时互相冲突，因此**先留在 fork，等 #23 合并后再单独提 PR**。

## 14. Qt 控制端远程文件管理器

【目标】不用给被控端新增协议：host 侧 `file-ops` 技能已经有
`list_directory` / `read_file` / `write_file` / `create_directory` / `move_file` /
`get_file_info`，控制端只要把工具调用发过去、把结果画出来即可。于是 Qt 侧的
「远程文件」抽屉（`RemoteWindow.qml` + `RemoteFileManager`）走的是现成的 skill bridge。

### 第一次是"静默失败"：请求根本没发出去

抽屉里的 `navigate()` / `submitPrompt()` 调用是 `mainController.remoteFiles.listDirectory(devId, path)`，
而 `devId` **在这个作用域里从来没有声明过**（抽屉自己的属性只有 currentPath/statusText/…）。
QML 抛 `ReferenceError: devId is not defined`，函数当场中断，工具调用一次都没发出去；
因为 QML 的运行期告警没有进 `app.log`，现象就是"点了没反应、日志里什么都没有"。

对照证据：同一条链路换 API 走（`skillExec`）45 ms 就返回，说明 bridge 本身没问题。

### 修法

- 抽屉里加 `activeDeviceId()`，用 `remoteWindow.connectionModel.deviceIdAt(currentTabIndex)`
  取当前标签页的设备号（和录制、文件传输按钮同一套取值方式）；
- 取不到设备号时把 `statusText` 设成 `No active connection`，不再"点了没反应"；
- `RemoteFileManager::sendTool()` 每次发包打一条 `RemoteFileManager: sending <tool> to <device> (id=…)`；
  `ClientManager::sendSkillCommand()` 的两个静默 early-return（messaging 未就绪 / 设备没有连接）
  也补上 `LOG_WARN`——以后这类"消息发不出去"在日志里能直接看出来。

### 实测（4.2.8.0 + Windows 11 被控端，同一台 VM 自控自）

全部动作都在 Qt 抽屉里点出来，再回被控端磁盘上核对：

| 动作 | 日志证据 | 被控端磁盘 |
|---|---|---|
| 打开抽屉 | `sending list_directory … (id=qt-files-1)` | `C:\` 20 项列出来 |
| 切到 `C:\QuickDeskFilesTest` | `sending list_directory … (id=qt-files-2)` | 列出 1 项 |
| New Folder → `ui-e2e-filemanager` | `sending create_directory … (id=qt-files-3)` + 自动 `list_directory` | 目录真的出现 |
| ✏️ 重命名 → `renamed-ok` | `sending move_file … (id=qt-files-13)` + 自动刷新 | `rename-me` 变成 `renamed-ok` |

## 15. 设备访问审计（谁在什么时候试图连我的机器）

【目标】远程控制产品必须能回答一句话：「有没有人试图打开我这台机器，从哪来，成没成」。
QuickDesk 原来只有**控制端视角**的连接历史（`/v1/me/connections`，由客户端自己上报），
被控端用户看不到别人对自己机器的尝试；失败尝试只落在日志和指标里，没有可查记录。

### 做法：服务端在验证口子上落库

新增 `device_access_logs`（模型 `internal/models/device_access_log.go` + 服务
`internal/service/device_access_service.go`），在**服务端唯一的口子**
`POST /v1/devices/:device_id/access-code:verify` 上记录一行，控制端无法伪造、也无法隐瞒：

| `result` | 触发点 |
|---|---|
| `granted` | 访问码匹配且 host 在线，签发 signal_token |
| `denied_invalid_code` | 访问码不匹配 |
| `denied_rate_limited` | 预检被限流挡住（per-IP / per-device / per-(device,ip)）或失败计数触顶 |
| `host_offline` | 访问码匹配但 host 不在线，不计入失败 |
| `session_started` | 控制端拿着 `granted` 换来的 token 真的把信令通道建起来了——"尝试"变成"真的连上了"，行里带 `session_id` |

行里带 `device_id / owner_id / client_id / session_id / ip / result / reason / created_at`。
`owner_id` 取当时的绑定者（没绑定时为 0）——这样"设备转手后"的历史仍然归属当时的所有者。
控制端身份目前只能是 **IP + client_id**：`access-code:verify` 走的是 API Key / Origin 白名单，
不是用户会话，服务端没有可归属的 user_id（这点在模型注释里写明了，避免以后误判）。

读接口（设备所有者限定）：

```
GET /v1/me/devices/:device_id/access-logs?limit=&cursor=
→ {items:[{id,device_id,owner_id,client_id,session_id,ip,result,reason,created_at}], next_cursor}
```

同时发事件：`device.access.granted` / `device.access.denied` / `device.access.session_started` 推给 **设备所有者**的
实时流（`/v1/realtime/events`）；拒绝类事件额外进管理员审计表（`audit_logs`），
这样"有人一直在试我的访问码"既是运维告警也是审计证据。

### 实测（本地自托管栈 + Parallels Windows 被控端）

| 断言 | 证据 |
|---|---|
| 表由 AutoMigrate 建出 | `\d device_access_logs` 显示 4 个索引，与 `migrations/001_init.sql` 一致 |
| 错误访问码 | `http=403 INVALID_CODE` → 行 `denied_invalid_code`，reason `access code is incorrect` |
| 正确访问码 | `http=200` + `signal_token` → 行 `granted` |
| 连续失败触发限流 | 第 5 次 `TOO_MANY_ATTEMPTS` → 行 `denied_rate_limited` / `too many failed attempts` |
| 限流预检拦截 | 再来一次 → 行 `denied_rate_limited` / `Too many failed attempts for this device from your IP` |
| host 离线 | 对离线设备用正确码 → `http=409 HOST_OFFLINE` → 行 `host_offline` |
| 所有者可查、可翻页 | `limit=3` 返回后 3 条并带 `next_cursor`，第二页 id 为 6/5/4（键集分页正确） |
| 越权被拒 | 另一个用户查同一设备 → `403 FORBIDDEN "Device is not owned by this user"`；不存在的设备 → `404 DEVICE_NOT_FOUND` |
| 实时事件 | 连上 `/v1/realtime/events` 后触发一次拒绝，收到 `{"type":"device.access.denied","server_rev":342,"data":{…"log_id":11}}` |
| 审计表 | `audit_logs` 落下 `device.access.denied`，details 里带 device_id / client_id / ip / reason |
| 真连上会另记一行 | 控制端 `connectToHost` 后先出 `granted`(id=13)，20 ms 后出 `session_started`(id=14, `session_id=sig_7a3663e1…`)——"验证过"和"真的连上"在时间线上是两件事 |
| 会话开始也推实时流 | 断开再连，实时流依次收到 `device.access.granted` 与 `device.access.session_started`（带 `session_id`） |

用到的探针：`scripts/e2e/realtime-access-events.mjs`（监听实时流里有没有
`device.access.*`，没有就退出码 3，可以直接当验证闸门）。

### 仍然没做

- 拒绝类事件还没有走 **webhook**：webhook 订阅的是系统级事件，而访问事件带 user_id，
  按 §2.17 M4 的规则不能直接广播给未绑定用户的 webhook；要做得先有"用户级 webhook/通知策略"；
- WebClient 还没有"访问记录"页面（等上游 PR #23 合完再动 WebClient 的路由/i18n，避免重复冲突）；
- 会话**结束**（时长）没有记录：`session_started` 已经落库，但信令 WS 断开不等于会话结束
  （网络抖动也会断开，客户端会自动重连），拿它当会话边界会算出一堆几秒的假会话；
  要算时长得先有统一 session 模型，或者让控制端显式上报结束。

## 16. 用户级通知通道（把事件真的推出去）

【目标】第 15 节做的 `device.access.*` 事件当时**没人能订阅**：管理端 webhook 只收系统级事件
（§2.17 M4 的隔离规则），用户级事件（带 user_id）不能广播给未绑定用户的 webhook。
所以「通知」这一项一直停在"有 webhook 基础设施"上。

### 做法：用户自己的 webhook

新增 `user_notification_channels`（模型 `internal/models/user_notification_channel.go`
加服务 `internal/service/notification_channel_service.go`），每个用户管自己的端点：

```
GET    /v1/me/notification-channels
POST   /v1/me/notification-channels            {name?, url, secret?, events:[...], enabled?}
PATCH  /v1/me/notification-channels/:id
DELETE /v1/me/notification-channels/:id
POST   /v1/me/notification-channels/:id/test   发一条 test，用来验端点
```

- 所有查询都按 `user_id` 收口，别人的通道既读不到也改不了；
- `secret` 用 `json:"-"`，只用于签名，永远不回显；
- 投递复用管理端 webhook 的那套：`X-Webhook-Signature: sha256=<hmac>`、3 次退避重试，
  并把 `last_status` / `last_triggered` 写回通道行（顺手把这段抽成 `postWebhook()`，两个服务共用）；
- 事件白名单是显式列表：`device.access.denied` / `granted` / `session_started`、
  `device.online.changed`、`device.bound` / `device.unbound`，
  拼错事件名在创建时就 400，而不是静默永不触发。

### 实测（本地自托管栈 + 真实事件源）

用一个本地接收器（`scripts/e2e/notification-receiver.mjs`，会自己核对 HMAC）接了三类真实投递：

| 触发 | 接收到的 payload | 签名 |
|---|---|---|
| `POST .../:id/test` | `{"event":"test","data":{"message":"This is a test notification from QuickDesk"}}` | 通过 |
| 一次错误访问码（403） | `{"event":"device.access.denied","data":{"client_id":"e2e-notify","ip":"127.0.0.1","reason":"access code is incorrect",...}}` | 通过 |
| 控制端真的连上 | `{"event":"device.access.session_started","data":{"session_id":"sig_620e997f-…","client_id":"client_126735214",...}}` | 通过 |

边界也一并测了：

| 断言 | 结果 |
|---|---|
| 非 http(s) URL | `400 INVALID_REQUEST "notification URL must be an absolute http(s) URL"` |
| 订阅系统级事件 | `400`，错误信息里列出支持的 event 名 |
| 创建响应不回显 secret | 响应体里没有 `secret` 字段 |
| 别的用户看不到 | 列表返回 0 条；拿别人的 id 删除 → `404`（不是 200） |
| 端点挂掉 | `last_status=0` 落库（重试耗尽后如实记录失败） |
| 投递成功 | 通道行 `last_status=200`、`last_triggered` 有值 |

### 仍然没做

- ~~投递没有持久队列~~ → **已在第 21 节补上**：现在是 `notification_deliveries` outbox，
  至少一次投递，接收端离线不丢事件；
- WebClient 还没有通道管理页面（等 PR #23 合完再动前端路由/i18n）；
- 没有聚合降噪：设备频繁上下线会对通道逐个推送，后面要加"窗口内合并/静默"策略；
- 用户级通道的 URL 是用户可控的，单租户自托管可以接受；对外做 SaaS 前要加出网白名单（SSRF）。

## 17. 设备级访问策略（谁能连我的机器）

【目标】第 15 节解决了"看得见谁在试"，但看见之后没法拦。被控端主人需要两件事：
「我现在不想被连」和「只允许这几个网段连」，而且拦截必须发生在**访问码比对之前**
——否则被拉黑的来源还能继续猜密码。

### 做法

新增 `device_access_policies`（一设备一行，没有行 = 不限制，保证升级后老设备照常可用）：

```
GET /v1/me/devices/:device_id/access-policy
PUT /v1/me/devices/:device_id/access-policy   {remote_disabled, allow_ips:["10.0.0.0/8","203.0.113.7"]}
```

- `remote_disabled=true`：任何来源都开不了新会话；
- `allow_ips`：裸 IP 或 CIDR 列表，留空表示不限制；客户端地址按**服务端看到的来源地址**匹配；
- 校验在服务端：非 IP / 非 CIDR 直接 400，不做"默默忽略"；
- 网关顺序：限流预检 → **策略** → 访问码比对 → host 在线检查 → 发 token。
  策略拦截不进入失败计数（被拉黑的人不该把正常用户的失败计数顶掉），但会记一条访问日志。

被拦下的尝试在访问时间线上是 `denied_policy`（新增的第五种 result），
原因写进 `reason`；同时照常发 `device.access.denied`，所以上一节的用户通知通道
不用改一行就能收到"有人被策略挡住了"。策略变更本身也进管理员审计
（`device.access_policy.changed`，details 里带当时的策略快照）。

### 实测（本地自托管栈 + 真实控制端）

| 断言 | 结果 |
|---|---|
| 没有策略行时 | `GET` 返回 `{remote_disabled:false, allow_ips:[]}`，真实控制端连接照常成功 |
| 只允许 VM 网段 `10.211.55.0/24` | 从 `127.0.0.1` 验证正确访问码 → `403 ACCESS_POLICY_DENIED` / `client IP is not in the device allow list`，并落 `denied_policy` 行 |
| 改成允许 `127.0.0.0/8` | 同一个请求立刻变成 `200` + `signal_token`（策略是即时生效的） |
| 打开"禁止远程访问" | 即使 IP 在白名单里也 `403` / `remote access is disabled for this device` |
| 非法 CIDR / 域名 | `10.0.0.0/99` 与 `example.com` 都 400，错误信息指到具体条目 |
| 越权 | 另一个用户 `GET`/`PUT` 同一设备 → 都是 `403` |
| 复位后回归 | 清空策略后再连一次，真实控制端 `granted` → `session_started` 正常 |
| 审计 | `audit_logs` 里能看到 `device.access_policy.changed`（带快照）与 `device.access.denied` |

### 仍然没做

- **会话策略**还没做：并发上限、允许时段、二次审批、临时一次性授权都还没有；
- 策略是"服务端看到来源地址"，生产上如果前面有反代/网关，得先确认 `X-Forwarded-For`
  与可信代理配置，否则白名单会按网关 IP 匹配；
- 策略变更没有推送事件给控制端 UI（WebClient/Qt 都不显示"这台机器现在禁止远程访问"）。

## 18. 会话级策略：并发控制上限

【目标】远程支持场景里最烦的事之一是两个人同时抢一台机器。上一节的策略管的是"谁能来"，
这一节补"同时来几个"：`max_sessions` 给每台设备一个控制端并发上限（0 = 不限）。

### 做法与一个被实测揪出来的协议坑

策略行加一列 `max_sessions`，接口就是同一个 `PUT .../access-policy`。校验点在**控制端信令
`auth_ok` 之前**：此时访问码已经验过（时间线上会先有一条 `granted`），所以拒绝不是"码错了"，
而是"机器已经有人在看了"，于是记成 `denied_session_limit`，并给 socket 回
`SESSION_LIMIT_REACHED`。

第一版把校验放在了 `auth_ok` 之后，实测立刻暴露问题：客户端**已经收到 auth_ok**、以为连上了，
紧接着才被踢——`scripts/e2e/signal-client-probe.mjs` 甚至退出了 0（成功）。把校验挪到
`auth_ok` 之前后，第二个控制端拿到的是：

```json
{"type":"error","code":"SESSION_LIMIT_REACHED","detail":"device allows at most 1 concurrent controller(s)"}
```

这条经验值得留着：**"先答应再反悔"在长连接协议里等于没有拒绝**，所有准入判断都必须在
第一帧 `auth_ok` 之前完成。

### 实测

| 断言 | 结果 |
|---|---|
| `max_sessions=-2` | `400` "max_sessions must be zero (unlimited) or a positive number" |
| 上限 1，第一个控制端 | `auth_ok`，`QD_HOLD_MS=25000` 占住名额 |
| 上限 1，第二个控制端 | `SESSION_LIMIT_REACHED`（**没有** auth_ok），探针退出码 3 |
| 访问时间线 | `36 slot-b granted` → `37 slot-b denied_session_limit`（码是对的，名额被占） |
| 调回 `max_sessions=0` | 第三个控制端立刻 `auth_ok`（时间线 `38 granted` → `39 session_started`） |

### 仍然没做

- 允许时段、二次审批、一次性临时授权都还没做；
- 上限只按"控制端信令连接数"算，不区分"只看不控"和"有输入权"——真正的"单人操作"锁
  还得结合墙页那套输入解锁；
- 被挤掉的控制端没有 UI 提示（只有协议层错误帧）。

## 19. 并发压测台（信令层）

【目标】第 18 节留了个没验的洞：「多个控制端同时抢名额」只测了两条 socket。顺手把 P1 里
「长稳、并发和 TURN 容量压测」的**并发**部分做成可复用的压测台。

### 工具

`scripts/e2e/signal-load.mjs`，两种模式：

```bash
# 突发：20 个控制端同时连，各自占住 5 秒
QD_SIGNAL_TOKEN=<client_token> QD_CLIENTS=20 QD_HOLD_MS=5000 node scripts/e2e/signal-load.mjs
# 轮转：5 轮 × 10 次「连上 → auth_ok → 断开」
QD_SIGNAL_TOKEN=<client_token> QD_ROUNDS=5 QD_CLIENTS=10 node scripts/e2e/signal-load.mjs
# 断言并发上限确实只放进 N 个
QD_SIGNAL_TOKEN=<token> QD_CLIENTS=20 QD_EXPECT_ACCEPTED=5 QD_EXPECT_REJECTED=15 node scripts/e2e/signal-load.mjs
```

输出每轮的 accepted/rejected/errors，以及连接延迟的 p50/p95/max 和拒绝码分布；
计数不符合预期退 3，出现传输层错误退 4，可以直接当闸门。

一个实现细节值得记：控制端 signal token 是**可复用**的（服务端对 client 走
validate-and-extend，留给断线重连），所以整轮压测只需要 `access-code:verify` 一次，
不会把每 IP 60 次/分钟的验证限流撞爆。

延迟统计只算「到服务端裁决为止」的时间：早期版本把 hold 时长也算进去了，
结果 p50 显示 5018 ms，等于把等待时间当成连接耗时——压测数字必须能说明它到底在量什么。

### 实测（本地自托管栈，单实例）

| 场景 | 结果 |
|---|---|
| 基线：20 个并发控制端，各自 hold 5s，无上限 | 20 accepted / 0 rejected / 0 errors；连接延迟 p50 **15 ms**、p95 24 ms、max 26 ms |
| 上限 5：20 个控制端同时抢 | **accepted=5、rejected=15，全部 `SESSION_LIMIT_REACHED`**，0 传输错误；p50 26 ms |
| 轮转：5 轮 × 10 次连接（共 50 次会话） | 50 accepted / 0 errors，wall 52 ms，p50 5 ms |
| 轮转后名额是否泄漏 | 把上限调成 1 再连一个：`auth_ok`（说明 50 次断开没留下僵尸名额） |
| 服务端内存 | 轮转前后 RSS 38912 KB → 39072 KB（+160 KB，8 秒后采样；只是烟测级信号，不是 soak 结论） |
| 访问时间线 | `session_started` 累计 105 行、`denied_session_limit` 17 行，与实际连接数吻合 |

### 仍然没做

- **TURN 容量**：本地 .env 里 TURN/STUN 是空的（同网段直连），要压 TURN 得先起 coturn
  并配 `TURN_URLS/TURN_AUTH_SECRET`，再用真实媒体流跑，信令压测台覆盖不到这一步；
- **长时间 soak**：现在是秒级烟测，没有跑小时级的稳定性/内存曲线；
- 压测只打信令面，没有同时压录像上传、文件传输这些带宽型接口。

## 20. 允许时段（只在某些时间能连）

【目标】策略已经能管「谁能来、来几个」，但最常见的诉求是「只在上班时间能连」。
这一节给同一行策略加 `allowed_windows` + `timezone`。

### 语义（写在文档里，避免以后各自理解）

```json
{"allowed_windows":[{"days":[1,2,3,4,5],"start":"09:00","end":"18:00"}],"timezone":"Asia/Shanghai"}
```

- `days`：`0`=周日 … `6`=周六，省略表示每天；
- `start`/`end` 是**该时区的墙钟时间**，`end` 不含；
- `start > end` 表示跨午夜，且**day 锚在窗口开始那天**：
  `{"days":[5],"start":"22:00","end":"06:00"}` 覆盖周五夜里到周六早上 6 点；
- 空列表 = 不限时段；不在任何窗口内的验证请求直接 `ACCESS_POLICY_DENIED` /
  "outside the allowed access window"，访问码根本不会被比对。

时区用 IANA 名（如 `Asia/Shanghai`），留空表示服务器本地时区；写入时用
`LoadLocation` 校验，乱填直接 400。为了让 `LoadLocation` 在不带 tzdata 的宿主
（Windows、scratch 容器）上也能工作，服务端 main 里显式 `import _ "time/tzdata"`。

### 一个差点阴人的坑：Go 的文件名就是编译约束

第一版把窗口求值写在 `internal/service/device_access_windows.go`，`go build` 立刻报
`undefined: AccessWindow` ——因为 **`_windows.go` 后缀会被 Go 当成 GOOS 约束**，
在 macOS/Linux 上这个文件根本不参与编译。在 Windows 上它反而会编进去：
如果没人看日志，代码会"在开发机上好好的、在 Linux 生产上功能凭空消失"。
改名为 `device_access_timewindow.go` 后正常。**除真的平台专用代码，不要用
`_windows.go` / `_linux.go` 这种后缀命名文件。**

### 实测（本地自托管栈，2026-10-16 周五 04:58 +08:00）

| 断言 | 结果 |
|---|---|
| 只允许周一 09:00-18:00（当天是周五） | `403 ACCESS_POLICY_DENIED` / `outside the allowed access window` |
| 改成周五全天 | 同一请求 `200` + `signal_token` |
| 跨午夜锚定：`days:[4] 22:00-06:00`（周四起算） | 周五 04:58 在窗口内 → `200` |
| 同一时刻、窗口锚在周五（`days:[5]`） | 不在窗口内 → `403`（证明 day 锚在开始日，不是"今天"） |
| `start:"9am"` / `days:[7]` / `timezone:"Mars/Phobos"` | 三个都是 `400`，错误信息指到具体窗口/字段 |
| `GET .../access-policy` | 回显 `allowed_windows` 与 `timezone` |
| 清空窗口后真实控制端 | `granted` → `session_started` 正常 |
| 访问时间线 | 被窗口挡下的那次记成 `denied_policy` / "outside the allowed access window" |

单元测试另外覆盖了边界（`end` 不含、周末排除、跨午夜、同一天空窗口算全天、
时区换算：UTC 03:00 = 上海 11:00 落在窗口内）。

### 仍然没做

- 节假日历/例外日（比如春节放假）没有；
- 窗口按"开始会话"判断，已经在会话里的连接不会被时段踢掉；
- 没有给控制端 UI 提示"现在是禁止时段"，只有协议层的 403。

## 21. 通知投递 outbox（离线不丢事件）

【目标】第 16 节的通知通道是"尽力而为"的：一个 goroutine 里打 3 次就结束，
接收端离线久一点事件就永久丢了。这一节把投递改成**持久 outbox，至少一次**。

### 做法：先落库，再投递

新增 `notification_deliveries` 表（模型 `internal/models/notification_delivery.go`
加服务 `internal/service/notification_delivery_service.go`）。事件一到，先把每个
（事件 × 通道）写一行 `pending`，再由后台 worker 去投，投递和事件源彻底解耦：

- `Enqueue` 只写一行，不发 HTTP，所以事件总线订阅者不会被网络拖住；
- worker 每 2s 一次，用 `SELECT ... FOR UPDATE SKIP LOCKED` 把到期行原子地翻成
  `delivering`（两个实例/两个 worker 也不会重复发同一行）；
- 成功（2xx）→ `delivered` + `delivered_at`；失败 → 指数退避
  （2s / 4s / 8s … 封顶 5m）重排；**8 次后**停成 `failed`（保留，不静默丢）；
- 每次尝试把 `last_status`（HTTP 码，传输错误为 0）+ `last_error` 写到行和通道行上；
- 新增 `GET /v1/me/notification-channels/:id/deliveries?limit=` 给运维看：排队了什么、
  试了几次、现在是 `pending`/`delivering`/`delivered`/`failed`。

管理端 webhook 那条路径没动：原来的 `postWebhook` 现在是循环调用抽出来的
`postWebhookOnce`（单次 POST + HMAC 签名），两个服务共用同一段签名逻辑。

### 实测（本地自托管栈，2026-10-16 05:07 +08:00）

接收端用 `scripts/e2e/notification-receiver.mjs`（自带 HMAC 校验），
通道先指向 `http://127.0.0.1:9199/qd`，**先不开接收端**：

| 断言 | 结果 |
|---|---|
| 通道离线时 `:id/test` | `202`，outbox 立刻有一行 `status=pending / attempts=1 / last_status=0`，`last_error` 是 `dial tcp ... connection refused`，`next_attempt_at` 在未来 |
| 接收端起来后 | 秒级重投成功，行变 `status=delivered / attempts=3 / last_status=200 / delivered_at` 有值 |
| 接收端校验签名 | `signature=true` |
| 通道行 | `last_status=200`、`last_triggered` 有值 |

**持久性（跨重启）证明**：接收端关掉 → 再发一条 `:id/test`（行 2 变 `pending`）→
**把信令服务杀掉重启** → 重启后行 2 仍在（`attempts=3`，期间 worker 又试过，
接收端还没起）→ 起接收端 → 行 2 变 `delivered / attempts=4 / last_status=200`。
也就是说排队的事件不依赖进程内存，重启不丢。

单测覆盖了退避曲线（`2s→4s→8s→16s`，之后单调递增到 5m 封顶，非正数按首次重试）
和错误信息映射（传输错误 → 原始 error，`0` → "transport error"，非 2xx → `HTTP xxx`）。

### 仍然没做

- **接收端幂等**：投递是 at-least-once，处理完才失败可能收到重复事件；约定用
  `event` + `timestamp` + `data.log_id` 做幂等键，但没有服务端去重；
- ~~死信重放~~ → **已在第 22 节补上**：`POST .../deliveries/:deliveryId/retry` 可手动重投；
- ~~多 worker 水平扩展没有验证~~ → **已在第 22 节验证**：8 个并发 claimer 抢 500 行，
  零重复领取；
- **投递历史清理/保留策略**：`notification_deliveries` 只增不删，量大以后要加 TTL/归档。

## 22. outbox 并发领取证明 + 死信重放

【目标】第 21 节把投递做成 outbox，但留了两个自己都没证据的点：
（1）claim 写了 `SKIP LOCKED`，可是只跑过一个 worker，没证明多实例真的不重复领；
（2）`failed` 的行会一直留着，但没有"手动重投"入口。

### 并发领取证明

`SKIP LOCKED` 是 Postgres 特性，所以这条验证放在一个需要真库的测试里：
`internal/service/notification_delivery_claim_test.go`，只有设置了
`QD_TEST_DATABASE_URL`（指向**一次性**库，测试会先 `TRUNCATE`）才跑，默认 `go test ./...`
里自动 skip，不会污染开发库。

```
docker exec qd-postgres psql -U quickdesk -d postgres -c "CREATE DATABASE quickdesk_claimtest OWNER quickdesk;"
cd SignalingServer
QD_TEST_DATABASE_URL="host=localhost port=5432 user=quickdesk password=quickdesk123 dbname=quickdesk_claimtest sslmode=disable" \
  go test -count=1 -run TestClaimDueIsExclusiveAcrossWorkers -v ./internal/service/
```

测试塞 500 行 `pending`，起 **8 个** goroutine 各自循环 `claimDue(batch=20)`，
汇总所有被领取的 id：

| 断言 | 结果 |
|---|---|
| 8 个并发 claimer 领满 500 行 | 500 行全部被领取，无一遗漏 |
| 任意一行被领取的次数 | 全部为 1，**零重复** |
| 结束时 `status='pending'` 的残留 | 0（没有 claimer 提前退出留下夹生行） |
| 连跑 5 次 | 5/5 稳定通过 |

**对照组（证明测试不是空跑的）**：临时把 SQL 里的 `FOR UPDATE SKIP LOCKED` 删掉
（退化成普通 `SELECT`）后重跑，8 个 worker 里有 **480/500 行被重复领取**，测试立刻 FAIL；
把子句恢复后重新变绿。也就是说这条断言确实在检验"领取互斥"这件事本身。

### 死信重放

新增 `POST /v1/me/notification-channels/:id/deliveries/:deliveryId/retry`
（owner-scoped，先校验通道归属，再按 `(id, channel_id)` 定位投递行）：

- 只有 `failed` 的行可重投，其余状态一律 `400 INVALID_REQUEST
  "only failed deliveries can be retried"`；
- 重投把行拉回 `pending`、`attempts` 归零、`next_attempt_at = now`，worker 下一个 tick
  就会再发一次；上一轮的 `last_error` 保留到下次尝试覆盖。

实测（本地栈，2026-10-16 05:11 +08:00）：直接种一条 `failed / attempts=8 /
last_error="HTTP 503 (synthetic dead-letter row)"` 的行，接收端起在 9199 后调 retry：

| 断言 | 结果 |
|---|---|
| retry 失败行 | 返回 `200`，行变 `pending / attempts=0` |
| worker 下一轮 | 行变 `delivered / attempts=1 / last_status=200` |
| 接收端 | 收到原始 payload、`signature=true` |
| retry 一条已投递的行 | `400 INVALID_REQUEST "only failed deliveries can be retried"` |
| retry 一个不归自己的通道 | `404 NOT_FOUND` |
| 清理 | 测试通道已删，`/v1/me/notification-channels` 恢复 0 条 |

### 仍然没做

- **接收端幂等**：at-least-once 语义不变，重放/重试都可能让接收端再收到一次；
  `event` + `timestamp` + `data.log_id` 是约定键，但服务端不做去重；
- **批量重放**：一次只能重投一条，没有"重放某通道所有 failed"的入口；
- **保留策略**：`notification_deliveries` 仍只增不删（重投后也保留原行），缺少 TTL/归档。
