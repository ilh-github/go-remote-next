# 会话录像引擎接入设计（远程控制媒体层）

> 范围：本文件只描述**远程控制会话的媒体录像（画面 + 声音）与回放接入**。
> 与 MCP 侧的「工作流录制与回放」（`quickdesk-mcp/src/workflow.rs`、
> `docs/dev/工作流录制与回放技术方案.md`）是**两套完全不同的系统**，不要混用
> 概念、字段或 API，详见第 0 节。

## 0. 文档定位与术语边界

| 维度 | 会话录像（本文件） | 工作流录制（另有一套） |
|---|---|---|
| 录制对象 | 远程桌面的音视频画面 | AI / MCP 的 tool call 序列 |
| 产物 | `.mp4` / `.webm` 媒体文件 + 缩略图 | `.json` 步骤文件（含屏幕 hash、OCR 关键词） |
| 触发者 | 控制端用户 / 被控端策略 | AI Agent（`start_recording` / `stop_recording`） |
| 落盘位置 | 控制端或被控端本地磁盘，再上传归档 | `~/.quickdesk/workflows/` |
| 服务端索引 | `session_recordings` 表 + `/v1/me/recordings` | 无（本地文件，可手工分享） |
| 回放语义 | 看视频，可拖动进度条 | 逐步重放 tool call，每步校验状态 |
| 涉及模块 | `QuickDesk/src/manager/*`、`WebClient/`、`SignalingServer/` | `quickdesk-mcp/` |

结论：两条链路只在「都叫录制」这一点上重合，**不共享存储、不共享 API、不共享
状态机**。本文后续所有「录制」默认指会话录像。

## 1. 现状盘点（基于当前代码，只读分析）

### 1.1 控制面（Signaling Server）已经有的部分

已经落地、可以直接复用的：

- 模型：`SignalingServer/internal/models/session_recording.go`
  - 字段：`id / user_id / device_id / device_name / session_id / status /
    format / artifact_path / artifact_url / thumbnail_path / duration_seconds /
    size_bytes / started_at / ended_at / created_at / updated_at`
  - 语义注释写得很清楚：**媒体文件由引擎持有，这张表只做可发现、可审计、可删除的索引**。
- 服务层：`SignalingServer/internal/service/session_recording_service.go`
  - `Create / Update / List / Get / Delete`
  - `status` 只允许 `recording | completed | failed`；`duration_seconds`、`size_bytes` 不许为负。
- 接口层：`SignalingServer/internal/handler/session_recording_handler.go` + `cmd/signaling/main.go:272-276`
  - `GET    /v1/me/recordings`
  - `POST   /v1/me/recordings`
  - `GET    /v1/me/recordings/:id`
  - `PATCH  /v1/me/recordings/:id`
  - `DELETE /v1/me/recordings/:id`
- 事件：`service.EventRecordingCreated / EventRecordingUpdated / EventRecordingDeleted`
  （`event_bus.go:54-56`），由 handler 在写库成功后 publish。
- 迁移：`SignalingServer/migrations/001_init.sql:97-117`（建表 + 三个索引）。
- 文档：`SignalingServer/docs/user-api-docs.md` §5.4 已登记这 5 个接口与事件。
- 管理面索引：`internal/handler/admin_session_recording_handler.go` 提供跨用户
  `GET /v1/admin/recordings`、`GET/DELETE /v1/admin/recordings/:id`（`main.go:391-393`），
  供审计/管理后台使用，**不复用用户接口**。

### 1.2 控制端已经有的部分

**Qt 控制端（`QuickDesk/`）**

- 与 Chromium 进程通信统一走 `NativeMessaging`（stdio JSON 或双命名管道），
  协议版本号 `kNativeMessagingProtocolVersion = 3`（`HostManager.cpp:11`）。
- `ClientManager`（`QuickDesk/src/manager/ClientManager.h`）是控制端会话的唯一权威：
  - 按 `deviceId` 管理会话；`ConnectionInfo.rtcState`（connecting/connected/disconnected/failed）
    就是可用的录制生命周期锚点。
  - 已暴露 `connectionStateChanged(deviceId, state, hostInfo)`、`connectionAdded/Removed`、
    `hostCapabilitiesChanged(...)`、`performanceStatsUpdated(deviceId, stats)`。
  - 已有文件传输的落盘先例：下载默认写 `QStandardPaths::DownloadLocation`
    （`ClientManager.cpp:606`），上传走 `startFileUpload`。
- 视频帧在 Qt 进程内是**可直接读的**：
  - `SharedMemoryManager`（`QuickDesk/src/manager/SharedMemoryManager.h`）里
    `SharedFrameHeader` 已带 `width / height / format(I420) / frame_index / timestamp_us /
    y_stride / u_stride / v_stride / data_size`；
  - `VideoFrameProvider::onVideoFrameReady(frameIndex)` 是现成的帧到达回调。
  - 也就是说：**控制端录制不需要改 Chromium，只需要把已有的 I420 帧交给编码器。**
- 本地路径统一由 `infra::ApplicationContext` 给出：`localDataPath()`
  （`QStandardPaths::AppDataLocation`）、`localDownloadPath()`、`logPath()`。

**Web 控制端（`WebClient/`）**

- 远程页面是 `remote.html` + `WebClient/js/remote-main.js`，WebRTC 收到的轨道已经合成
  `MediaStream`（`remote-main.js:442-447`、`718-723`）。
  这意味着浏览器侧用 `MediaRecorder` 录这个 `MediaStream` 是现成的、零后端改动。
- 录像列表页已经存在：`WebClient/src/views/RecordingsPage.vue`（296 行），路由 `/recordings`，
  i18n key `recordings.*`，API 封装在 `WebClient/src/api/userApi.js:397-414`
  （`fetchRecordings / fetchRecording / deleteRecording`）。
  页面已经实现了「列表 / 状态徽标 / 时长 / 大小 / 播放 / 下载 / 删除 / 分页」，
  并且**只在 `artifact_url` 存在时才给播放和下载按钮**，否则提示
  “录制引擎尚未为该会话发布可播放的文件”。
- 外部集成面：`QuickDesk/src/api/WebSocketServer.cpp` 是 Qt 对外 JSON-RPC WS
  （默认端口 9600），`ApiHandler` 注册方法，`SecurityManager` 做鉴权/限速/危险操作拦截；
  OCR 类重方法走线程池（`kAsyncMethods`）。

### 1.3 媒体链路现状

```
被控端                          控制端
Chromium host(quickdesk_host)   Chromium client(quickdesk_client)
   │ 采集 → 编码(H.264/VP8/VP9/AV1) │ 解码
   │ WebRTC ────────────────────► │
   │                               │ 写入共享内存(I420, 带 timestamp_us)
   │                               ▼
   │                       Qt: SharedMemoryManager → VideoFrameProvider
   │                       Web: MediaStream → <video>
```

要点：

- **帧率/分辨率/编码由 Chromium Remoting 决定**，Qt 与 Web 只是消费端，不重写采集与编码。
- Qt 侧拿到的已经是**解码后的 I420**，落盘需要二次编码；Web 侧拿到的是 `MediaStream`，
  可以直接录，但格式受 `MediaRecorder` 限制（Chrome 上实际是 WebM/VP8|VP9|H.264）。
- 控制面（Signaling Server）目前**没有任何媒体字节通道**：
  `grep` 全仓未发现 `multipart` / `FormFile` / `r.Static` / 静态目录挂载，
  `artifact_url` 目前没有任何服务端生产者。

### 1.4 缺口清单

| # | 缺口 | 影响 | 归属 |
|---|---|---|---|
| G1 | 没有录像启停的媒体引擎 | 表里有行，永远没有文件 | Host / Qt / Web |
| G2 | 没有录像文件上传通道 | `artifact_url` 无法填写，Web 端永远“暂无可用媒体” | Signaling Server |
| G3 | 没有缩略图生成 | `thumbnail_path` 恒为空 | 引擎 |
| G4 | 没有崩溃恢复 / 幂等上传 | 断线或进程崩溃会留下孤儿 `.part` 与重复行 | 引擎 + 服务端 |
| G5 | `session_id` 语义未定义 | 一次 WebRTC 里有 host ws 与多个 client ws 的 `sig_*` | 契约 |
| G6 | 无保留期/权限策略 | 录像可能被无限期留存或被非 owner 直接下载 | 服务端 |
| G7 | `recording.updated` 未推到用户事件 WS | 录制结束后列表页不会自动更新 | Signaling Server |

G2/G5/G7 是**必须在做引擎之前先定契约**的项，否则引擎做出来也接不上。

## 2. 录制点选型：谁写文件

这是本设计最关键的决策，先给出结论，再给推导。

### 2.1 候选点对比

| 方案 | 帧来源 | 是否改 Chromium | 文件质量 | 可信度（防篡改） | 成本 | 结论 |
|---|---|---|---|---|---|---|
| A. 被控端 Host 进程录制 | 采集后原始 I420 / 编码后码流 | **是**（fork quickdesk-remoting） | 最高（源分辨率、无二次编码） | 最高 | 高（要编 Chromium） | P2 做权威录像 |
| B. 控制端 Chromium client 录制 | 接收到的编码码流 | **是** | 高（复用流编码，无需重编码） | 中 | 中高 | 不做（性价比差） |
| C. Qt 控制端录制 | 共享内存 I420 | 否 | 中（需二次编码） | 中 | 中 | **P1 先做** |
| D. Web 控制端录制 | `MediaStream` | 否 | 中（WebM） | 低 | 低 | **P0 先做** |
| E. 服务端/中继录制 | 无（QuickDesk 无中转数据面，WebRTC P2P/TURN） | 不适用 | — | — | — | 不做 |

### 2.2 决策

1. **一期（P0/P1）：控制端录制。**
   - Web 端用 `MediaRecorder` 录 `MediaStream`（半天量级）。
   - Qt 端用独立录制线程消费 `SharedMemoryManager` 的 I420 帧，按
     `SharedFrameHeader.timestamp_us` 的真实时间轴编码 mux。
   - 完全不碰 `quickdesk-remoting`，符合仓库铁律「不要为了一个功能去编译 Chromium」。
2. **二期（P2）：被控端权威录制。**
   - 触发条件：出现「合规要求由被控端留存、控制端不可信」的需求时启动。
   - 成本明确写在这里：fork `barry-ran/quickdesk-remoting` → 新增 Host 侧
     VideoRecorder（复用采集帧，避免二次编码）→ 新增 native-messaging 命令 →
     编译 Chromium 发布自有 remoting 包。
3. **不做**：控制端 Chromium client 录制。它同样要改 Chromium，却没拿到
   “源端权威”的收益，是 A 和 C 之间最差的一格。

### 2.3 单写者原则（避免双写）

- 一次录制只允许**一个 writer 角色**落盘：`source = host | control_qt | control_web`。
- 允许同一次会话存在两条录像行（一条控制端、一条被控端），但必须靠 `source` 区分，
  **不允许两个 writer 写同一个文件路径**。
- 录像行与文件的对应关系是 1:1（一期不分片），未来要分片再引入 `segment_index`。

## 3. 录制引擎设计

### 3.1 生命周期与角色

```
录像行(status=recording) ──► 文件(mp4/webm) ──► 缩略图 ──► 上传 ──► 行(status=completed)
                                   │
                                   └─ 失败/崩溃 ──► 行(status=failed, error_code)
```

角色分工：

| 角色 | 职责 |
|---|---|
| 触发者 | 控制端用户（Qt/Web 按钮）、或策略（被控端策略 / 服务端下发） |
| writer | 实际写文件的进程：Qt 录制线程 / 浏览器 MediaRecorder / Host 进程 |
| 索引者 | 始终是**控制端 Qt 或浏览器**：调 `POST`/`PATCH /v1/me/recordings` 上报元数据 |
| 归档者 | Signaling Server（二期）：接收上传、生成 `artifact_url`、做鉴权分发 |

> 为什么索引者不是 Host：沿用 §2.23 的既有结论——业务层集中在 Qt，
> Host 只保留「生命周期关键」的 HTTP 调用。Host 录制时，元数据通过
> native-messaging 回传 Qt，再由 Qt 上报（与 `access_code` 上报同一条路子）。

### 3.2 启停触发（明确「谁触发」）

| 场景 | 触发者 | 命令路径 |
|---|---|---|
| 用户点「开始录制」 | 控制端用户 | Qt：QML → `ClientManager::startRecording(deviceId)`；Web：页面按钮 → `MediaRecorder.start()` |
| 用户点「停止录制」 | 控制端用户 | 同上，`stopRecording` / `MediaRecorder.stop()` |
| 会话建立后自动录制 | 控制端本地设置 | `ClientManager` 在 `rtcState == connected` 时按设置自动 start |
| 会话结束自动停止 | 系统 | `ClientManager` 收到 `connectionStateChanged(disconnected\|failed)` 或 `connectionRemoved` 时强制 stop |
| 被控端策略强制录制 | Host 侧策略 | Host → `recordingPolicyChanged` → Qt 据此 start（P2） |

硬约束：

- **停止必须幂等**：重复 stop、断线后迟到 stop、进程退出时的 stop，都必须安全。
- **掉线不能丢文件**：会话异常结束时也要走 finalize（写 moov / 关文件），
  失败则保留 `.part` 与 journal 供恢复（见 3.6）。

### 3.3 文件格式

| 场景 | 格式 | 理由 |
|---|---|---|
| Qt 控制端（P1） | `.mp4`（H.264 + 可选 AAC） | 浏览器 `<video>` 原生可播、seek 友好、剪辑工具体验最好 |
| Web 控制端（P0） | `.webm`（VP8/VP9 + Opus） | `MediaRecorder` 唯一务实选项，先跑通链路 |
| 被控端 Host（P2） | `.mp4` | 与 Qt 端统一，避免下游再适配 |
| 备选/内部 | `.mkv`、裸 `.h264` | `.mkv` 容错好（崩溃可救），裸 `.h264` 体积小但无时间戳；都不作为对外格式 |

- Web 端产出的 `.webm` 在一期**只做本地下载**，不进服务端索引；二期由服务端
  ffmpeg 转封装/转码成 `.mp4` 后再发布 `artifact_url`（能 `-c copy` 就 copy，不能就转码）。
- `format` 字段直接落 `mp4 | webm`，与现有模型注释一致（原来还提过 `grf`，本项目不用）。
- 音频：声道跟随会话；`includeAudio` 作为录制参数，一期默认开。

### 3.4 目录与命名

**Qt 控制端（一期）**

```
<AppDataLocation>/recordings/<deviceId>/<yyyyMMdd>/<sessionId>_<recordingId>.mp4
<AppDataLocation>/recordings/<deviceId>/<yyyyMMdd>/<sessionId>_<recordingId>.thumb.jpg
<AppDataLocation>/recordings/<deviceId>/<yyyyMMdd>/<sessionId>_<recordingId>.json     # sidecar 索引
<AppDataLocation>/recordings/<deviceId>/<yyyyMMdd>/<sessionId>_<recordingId>.part     # 录制中
<AppDataLocation>/recordings/queue.json                                              # 待上报队列
```

（`<AppDataLocation>` = `ApplicationContext::localDataPath()`，Windows 上是
`%APPDATA%/QuickDesk` 一类路径，macOS 是 `~/Library/Application Support/QuickDesk`。）

**被控端 Host（二期）**

```
%LOCALAPPDATA%\QuickDesk\recordings\<deviceId>\<yyyyMMdd>\<sessionId>_<recordingId>.mp4
```

**服务端归档目录（二期）**

```
<media_root>/recordings/<user_id>/<yyyyMM>/<recording_id>.mp4
<media_root>/recordings/<user_id>/<yyyyMM>/<recording_id>.thumb.jpg
```

命名规则统一：`sessionId` 用服务端 `auth_ok.session_id`（形如 `sig_<uuid>`），
`recordingId` 用服务端返回的录像行 `id`；本地录制开始时服务端行还没建，先用
客户端生成的 `client_uid`（UUID）占位，上报成功后回填 `id`（见 3.6）。

### 3.5 缩略图

- 采样点：录制开始后第 3 秒的**关键帧**（不足 3 秒则取第一帧）。
- 规格：JPEG，宽 320px，等比缩放；不放大低分辨率帧。
- 落盘：与媒体文件同目录、同名前缀加 `.thumb.jpg`。
- 上报：`thumbnail_path`（本地绝对路径）与 `thumbnail_url`（二期服务端归档后）。
- 生成时机：录制停止（finalize 完成）后，从已封装的 mp4 里抽帧，避免扰乱录制热路径。

### 3.6 状态上报与失败恢复

**上报时序（正常）**

```
1. start  → 本地开始写 .part + journal；POST /v1/me/recordings  {status:"recording",
            client_uid, device_id, device_name, session_id, source, format, started_at}
            → 服务端返回 id，本地把 id 写回 journal
2. stop   → finalize（写 moov、close）→ 生成缩略图 → 计算 size/sha256
            → PATCH /v1/me/recordings/:id {status:"completed", format, artifact_path,
              thumbnail_path, duration_seconds, size_bytes, ended_at}
3. 上传     →（二期）POST /v1/me/recordings/:id/artifact → 服务端回 artifact_url
              → PATCH {artifact_url}
```

**失败恢复**

| 失败点 | 处理 |
|---|---|
| 录制中进程崩溃 | 重启后扫描 `*.part` + `*.json` journal；能修复就修复，否则把 `status=failed`、`error_code=ENGINE_CRASH` 上报 |
| finalize 失败 | 保留 `.part`，同上走 failed 上报，不删原文件 |
| `POST` 失败 | 写入本地 `queue.json`（或 Web 用 IndexedDB），指数退避重试；录制本身不受影响 |
| `PATCH` 失败 | 同上，队列重试；`status` 停留在 `recording`（前端显示“录制中”，可接受） |
| 上传中断 |（二期）分片 + 断点续传，行状态保持 `recording`，不产生 `completed` 假象 |
| 重复上报 | 服务端按 `(user_id, client_uid)` 幂等；无 `client_uid` 时靠 `id` 幂等 |

`client_uid` 是**新增需求**：现有表没有该列，缺它就无法安全重试 `POST`（会产生重复行）。

### 3.7 隐私与权限

- **被控端知情**：录制期间，被控端 UI（系统托盘 / 主窗口）必须显示持续可见的录制指示；
  若录制由控制端发起，被控端应显示“正在被 <控制端> 录制”。
- **隐私屏**：`privacyScreen` 打开时默认暂停录制（画面已被遮挡，录下来也没有意义），
  恢复后继续；如果产品要求“隐私屏期间继续录制”，必须由被控端显式确认。
- **权限**：发起点录和解（`POST`/`PATCH`/`DELETE /v1/me/recordings`）走 Bearer user token，
  天然 user-scoped；管理员审计查看走**单独**的管理员接口
  （`/v1/admin/recordings`，已存在），不复用用户接口。
- **播放/下载鉴权**：`artifact_url` 禁止裸静态目录，必须是
  `GET /v1/me/recordings/:id/artifact`（校验归属 + 支持 `Range`）或短时签名 URL。
- **不落敏感字段**：`access_code`、`signal_token`、剪贴板原文、设备 `device_secret`
  一律不进录像元数据、不进 sidecar、不进日志。
- **保留期**：建议新增 `retention_expires_at`（默认 30 天，管理员可配），
  到期由后台任务删除对象与行；删除录像必须同时删元数据与对象。
- **删除语义**：用户删除默认硬删（行 + 对象）；如需审计留痕，改为软删并记录删除审计。

## 4. 与 Signaling Server 现有录像 API 的对接

### 4.1 直接复用（不改）

- `POST /v1/me/recordings`：录制开始时建行（`status=recording`）。
- `PATCH /v1/me/recordings/:id`：录制结束时收口（`status/size/duration/ended_at/artifact_*/thumbnail_path`）。
  服务端已支持部分字段更新，指针语义不会把未传字段清空（`session_recording_service.go:113-172`）。
- `GET /v1/me/recordings`、`GET /v1/me/recordings/:id`、`DELETE /v1/me/recordings/:id`：列表页直接可用。
- 事件 `recording.created / recording.updated / recording.deleted`：已存在（`event_bus.go:54-56`）。

### 4.2 需要补的最小扩展

| 项 | 现状 | 建议 |
|---|---|---|
| 幂等键 | 无 | 表加 `client_uid`，`POST` 时若 `(user_id, client_uid)` 已存在则返回既有行 |
| 媒体上传 | **没有** | `POST /v1/me/recordings/:id/artifact`（先做整包上传，二期分片） |
| 媒体下载/播放 | **没有** | `GET /v1/me/recordings/:id/artifact`，校验归属 + 支持 `Range` |
| 录制来源 | 无字段 | 表加 `source`（`host` / `control_qt` / `control_web`） |
| 失败原因 | 无字段 | 表加 `error_code` / `error_message`，前端才能区分“没录上”和“录了但传丢” |
| 事件推送 | `recording.*` 未进用户事件 WS | 在 `/v1/realtime/events` 推送，前端收到 `recording.updated` 直接 patch 本地列表（遵循 §2.8「不要全量 refetch」） |
| `session_id` 语义 | 未定义 | 契约写明：取**控制端连接**对应的 `auth_ok.session_id`（`sig_<uuid>`）；Host 侧会话另行记录 |

注意：`webhookEligibleTypes`（`event_subscribers.go:28-32`）只放系统级事件，
`recording.*` 是 user-scoped，**不应**进 webhook 广播，否则会跨用户泄漏。

## 5. 协议消息设计

### 5.1 Qt ↔ Chromium 进程（native-messaging）

当前 `protocol_version = 3`（`HostManager.cpp:11`）。新增录制字段时**升到 4**，
并按既有规则处理版本不匹配（`nativeMessagingProtocolMismatch` → UI 提示升级）。

| 方向 | 消息 | 说明 |
|---|---|---|
| Host → Qt | `hostCapabilities {…, supportsSessionRecording:true}` | 复用现有能力上报（`ClientManager::handleHostCapabilities` 已在解析该消息，扩展一个字段即可） |
| Host → Qt | `helloResponse {…, recordingSupported:true}` | 早期能力探测 |
| Qt → Host | `startRecording {recordingId, sessionId, formatHint:"mp4", includeAudio, maxSeconds}` | P2 被控端录制 |
| Qt → Host | `stopRecording {recordingId}` | 幂等 |
| Host → Qt | `recordingStarted {recordingId, startedAt}` | 用于状态机进入 `recording` |
| Host → Qt | `recordingStateChanged {recordingId, state, message}` | 状态同步 |
| Host → Qt | `recordingStopped {recordingId, artifactPath, thumbnailPath, format, sizeBytes, durationSeconds, errorCode}` | 元数据回传，Qt 负责上报服务端 |
| Host → Qt | `recordingPolicyChanged {autoRecord, reason}` | 被控端策略（可选） |

一期（控制端录制）**不需要**新增 native-messaging 消息，只扩展能力字段即可。

### 5.2 Qt 对外 API（WebSocketApiServer + ApiHandler）

新增 3 个方法，供 Qt 内部 QML 之外的自动化/集成使用：

| 方法 | 参数 | 权限 | 备注 |
|---|---|---|---|
| `startSessionRecording` | `{deviceId}` | FullControl | 加进 `kAsyncMethods`（要等编码器就绪，别堵 UI 线程） |
| `stopSessionRecording` | `{deviceId}` | FullControl | 幂等 |
| `getSessionRecordingStatus` | `{deviceId}` | ReadOnly+ | 返回状态机快照 |

安全注意：这三个方法**不是**危险操作（不在 `SecurityManager::isDangerousOperation`
黑名单语义内），但必须走 `SecurityManager` 审计日志，便于日后追责。

### 5.3 Web 控制端 ↔ 服务端

```
开始：POST /v1/me/recordings            {status:"recording", source:"control_web", client_uid, …}
结束：PATCH /v1/me/recordings/:id       {status:"completed", duration_seconds, size_bytes, ended_at}
上传：（二期）POST /v1/me/recordings/:id/artifact
实时：/v1/realtime/events               recording.created / recording.updated / recording.deleted
```

一期 Web 端只做 `MediaRecorder` → 用户本地下载，**不建服务端索引**（避免出现
“有行无文件”的脏数据）；二期引入上传后再打开索引。

## 6. UI 状态机

统一状态定义（Qt 与 Web 共用同一组枚举名）：

```
idle ──start──► starting ──ok──► recording ──stop──► stopping ──ok──► finalizing
  ▲                 │                 │                   │              │
  │                 └──error──┐       └──session end──────┘              ├─ok──► completed
  │                           ▼                                          └─error─► failed
  └──────────────reset────────┴──────────── failed ◄───────────────────────────┘
```

附加分支：`completed → uploading → uploaded`（二期）。

| 状态 | 语义 | UI 表现 |
|---|---|---|
| `idle` | 未录制 | 录制按钮可点 |
| `starting` | 编码器/文件句柄准备中 | 按钮转圈、禁用 |
| `recording` | 正在写文件 | 红点 + 计时 + 当前体积 |
| `stopping` | 用户已点停止，等待最后一帧 | 按钮禁用 |
| `finalizing` | 封装、抽缩略图、算校验 | 显示“处理中” |
| `completed` | 本地文件就绪 | 提示“录像已保存”，可打开目录 |
| `failed` | 任一步失败 | 显示 `error_code` 对应文案 + 重试/打开目录 |

**Qt 侧映射**

- `ClientManager` 新增：`Q_INVOKABLE startRecording(deviceId) / stopRecording(deviceId)`，
  信号 `recordingStateChanged(deviceId, state, info)`、`recordingProgressChanged(deviceId, seconds, bytes)`。
- QML：在 `QuickDesk/qml/views/RemoteWindow.qml` 顶层工具栏加录制按钮 + 状态徽标；
  逐设备（tab）维护状态，切 tab 不丢状态。
- 自动停止钩子：监听现有 `connectionStateChanged` / `connectionRemoved`。

**Web 侧映射**

- 远程页 `remote.html`（`WebClient/js/remote-main.js`）加录制按钮，
  状态保存在页面内存（刷新即丢失，属预期行为）。
- 列表页 `WebClient/src/views/RecordingsPage.vue` **本期不改**；
  二期在收到 `recording.updated` 事件后 patch 列表，而不是整表重拉。

## 7. 数据库字段映射

现有 `session_recordings`（`migrations/001_init.sql:97-113`）与本设计的对应关系：

| 字段 | 引擎写入方 | 值 |
|---|---|---|
| `user_id` | 服务端 | 从 Bearer token 推导，客户端不可指定 |
| `device_id` / `device_name` | 控制端 | 被控端 9 位设备号 + 备注名 |

| `format` | 控制端 | `mp4` / `webm` |
| `artifact_path` | 控制端/引擎 | 引擎本地绝对路径（仅服务端/管理侧可见） |
| `artifact_url` | 服务端 | 二期：`/v1/me/recordings/:id/artifact` |

建议新增字段（写进 `migrations/001_init.sql` 并同步 `user-api-docs.md`）：

| 新增字段 | 类型 | 用途 |
|---|---|---|
| `source` | `VARCHAR(16)` | `host` / `control_qt` / `control_web`，解决单写者冲突 |
| `client_uid` | `VARCHAR(36)` | 客户端 UUID，`UNIQUE(user_id, client_uid)`，保证 `POST` 幂等 |
| `error_code` / `error_message` | `VARCHAR(32)` / `VARCHAR(255)` | 失败原因可展示 |
| `artifact_sha256` | `CHAR(64)` | 完整性校验 |
| `uploaded_at` | `TIMESTAMPTZ` | 二期上传完成时刻 |
| `retention_expires_at` | `TIMESTAMPTZ` | 保留期，GC 依据 |

状态迁移约束（服务端校验，防止前端乱改）：

```
recording → completed | failed
completed → (终态，不可回退)
failed    → (终态)
```

## 8. 建议的下一步实现顺序

先契约、再引擎、最后分发。每一步都能独立验证，不要求一次做全。

1. **契约收口（服务端）**
   表加 `source / client_uid / error_code / artifact_sha256 / uploaded_at / retention_expires_at`；
   `POST` 按 `client_uid` 幂等；`recording.*` 事件接入 `/v1/realtime/events`；同步 `user-api-docs.md`。
2. **Qt 控制端录制引擎（P1 主体）**
   新增 `DeviceRecorder`（独立线程）：消费 `SharedMemoryManager` 的 I420 帧 → libav mux `.mp4`；
   写 `.part` + journal；`ClientManager` 挂 `start/stop` 与自动停止钩子；QML 录制按钮 + 状态。
3. **本地索引队列与上报**
   `queue.json` + 指数退避；`POST`(recording) → `PATCH`(completed/failed)。
4. **缩略图**
   finalize 后抽帧生成 `.thumb.jpg`，回填 `thumbnail_path`。
5. **崩溃恢复**
   启动扫描 `.part` + journal，修复或标记 `ENGINE_CRASH`。
6. **Web 控制端录制（P0 铺路）**
   `remote.html` 加 `MediaRecorder`，本地下载；验证 WebM 播放与体积。
7. **媒体分发（服务端）**
   `POST/GET /v1/me/recordings/:id/artifact`（先整包，二期分片 + `Range`），
   填 `artifact_url`，让 `RecordingsPage.vue` 的播放/下载按钮真正可用。
8. **WebM → MP4 归档转码**
   服务端 ffmpeg 后处理，统一对外格式。
9. **被控端权威录制（P2）**
   fork `quickdesk-remoting`，Host 侧 VideoRecorder + native-messaging 命令 + 协议版本 4；
   自建 remoting 发布流程。
10. **策略与运维**
    保留期 GC、管理员审计查询、容量与并发压测、告警。

## 9. 容量与并发（估算与边界）

- 单机并发录制建议**上限 1 路**（Qt 侧二次编码吃 CPU；可配置，但默认保守）。
- 码率参考：1080p30 H.264 约 2–4 Mbps → 1 小时约 0.9–1.8 GB；
  720p 约 1–2 Mbps → 1 小时约 0.45–0.9 GB。
- 录制不得影响视频播放延迟：编码必须在独立线程/独立进程，且要有丢帧保护
  （队列积压超阈值时丢帧并记录 `dropped_frames`，而不是让画面卡住）。
- 服务端二期上传要考虑带宽限速与并发上限（单用户同时 1 路上传）。

## 10. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| Qt 二次编码 CPU 占用高 | 高 | 独立线程 + 硬件编码优先 + 码率/分辨率可配 + 丢帧保护 |
| 崩溃导致 mp4 无 moov 不可播 | 中 | 边录边写 `.part` + journal；必要时用 `.mkv` 过渡或 remux 修复 |
| `artifact_url` 无生产者导致功能“假接通” | 高 | 在 G2 关闭前，UI 明确显示「暂无可用媒体」而不是空白按钮（现状已如此） |
| 录像被非 owner 获取 | 高 | 带鉴权的下载端点 / 短时签名 URL；禁止裸静态目录 |
| 被控端不知情被录制 | 高 | 被控端录制指示灯 + 隐私屏暂停 + 策略可查 |
| 上游 remoting 停更 | 中 | P2 才 fork；先固定版本、后同步，避免过早背上 Chromium 编译债 |
| 与 MCP 工作流录制概念混用 | 中 | 本文件第 0 节 + 命名隔离（媒体录像 vs 工作流） |
