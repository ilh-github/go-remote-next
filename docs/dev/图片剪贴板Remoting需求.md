# 双向图片剪贴板 Remoting 需求

**状态**：2026-10-25，待 `quickdesk-remoting` 提供剪贴板图片的编解码与传输能力。

**对应清单**：QD-007 / QD-406。

**前置事实**：本文的所有现状判断都来自当前代码，不是推测。

**边界**：本文不要求在 fork 里另建一条媒体通道，也不接受把图片塞进现有控制通道。

## 1. 要解决的问题

截图是远程办公里最高频的剪贴板内容之一。当前实现只同步文本：

- `WebClient/js/input/clipboard-handler.js` 的上行只用 `navigator.clipboard.readText()`，
  下行在 `_onRemoteClipboard` 里写死 `if (mimeType === 'text/plain')`，
  其它 MIME 被静默丢弃——消息已经到达，只是没有人处理；
- 协议里 `clipboardEvent` 已经带 `mimeType` 字段，所以这不是"协议没有表达力"，
  而是**两端都没有实现图片路径**；
- Host 侧要把桌面上的位图写进系统剪贴板，需要平台 API（Windows/macOS/Linux 各不同），
  这是预编译 Remoting 二进制内部的能力，fork 无法在外围完成。

## 2. 现状：两条通道的容量差异（决定方案的关键）

同一个 `datachannel-handler.js` 里已经有两条成熟路径，容量完全不同：

| 路径 | 通道 | 分片 | 背压 |
|---|---|---|---|
| 剪贴板文本 | `controlChannel`，单条 JSON 控制消息 | 无 | 无 |
| 文件传输 | 独立 `filetransfer-<transferId>` DataChannel | 8 KB | `bufferedAmount > chunkSize * 8` 时暂停 |

一张 1920×1080 的 PNG 约 1~3 MB，一张 4K 截图可达 10 MB 以上。走控制通道意味着：

- 单条控制消息达到兆字节级，而控制通道同时承载输入事件、光标、分辨率等实时消息；
- 没有分片就没有断点续传，没有背压就把内存压力转嫁给主线程；
- 大消息会延迟同通道上所有其它消息，直接损伤操控手感。

因此图片必须复用**文件传输那条独立通道 + 分片 + 背压**的模式，而不是扩展控制消息。

## 3. 推荐方案

### 3.1 格式协商

两端在会话建立时交换支持的图片格式，取交集：

- 控制面新增 `clipboardImageCapabilities`：声明的 MIME 列表、单张大小上限、
  是否支持多张（剪贴板可以同时含多个项目）；
- 协商结果落在会话上，任一端能力变化时重新协商，不要缓存到磁盘；
- 至少支持 `image/png`；`image/jpeg` 作为高压缩可选项，由 Host 声明是否支持；
- 不做格式转换：要求端不支持的格式时明确失败，而不是静默转码——
  静默转码会改变用户放在剪贴板里的东西。

### 3.2 传输

- 独立 DataChannel，命名对齐文件传输：`clipboardimage-<transferId>`；
- 分片大小沿用 8 KB，背压阈值同文件传输；
- 元数据消息先走：MIME、字节数、宽高（用于 UI 提示，不用于校验）、
  多张时的序号与总数、传输 ID；
- 传输 ID 单向递增，与现有剪贴板审计的 transfer ID 语义一致；
- 取消语义对齐文件传输：任一端可取消，取消后通道关闭并清理缓冲。

### 3.3 控制面保留什么

控制通道只保留一个小消息：`clipboardEvent` 带 `mimeType: image/*` 与
"该图片在哪个独立通道上"，不承载图片字节。这样控制通道的延迟特性不变。

## 4. 权限与安全要求

- **审计照旧不存内容**：QD-909 已确立「记方向、MIME、字节数，不存文本」。
  图片照此办理，且**不得额外存储缩略图或感知哈希**——缩略图同样是内容。
  字节数已足以回答「14:03 拷走了多大一张图」。
- **大小上限双端强制**：协商声明的上限要在发送前和接收前各检查一次，
  超限直接失败并上报，不要把大图硬塞进通道。
- **多张与批量**：剪贴板同时含多个项目时，要么全量按序传输并在元数据里声明总数，
  要么明确不支持。不要传一半。
- **隐私屏/锁屏**：被控端处于隐私屏或锁屏状态时，不得读取或发送剪贴板图片；
  这与现有隐私屏语义一致，不在剪贴板层绕过。
- **不落盘**：图片只在内存中流转，不写临时文件。写盘会把一次剪贴板同步
  变成一次持久的文件泄漏。
- **权限提示**：浏览器侧读取剪贴板图片需要 `clipboard-read` 权限，
  失败路径要与文本失败一致地静默，不要每次轮询都弹错。

## 5. 验收用例

1. 控制端复制一张 PNG，Host 剪贴板得到同一张图，逐字节一致；
2. Host 复制一张图，控制端剪贴板得到同一张图，逐字节一致；
3. 协商：一端只声明 `image/png`，另一端发 `image/jpeg` 时明确失败而非静默转码；
4. 超过协商大小上限的图被两端各自拒绝，通道不建立；
5. 大图（≥ 4 MB）传输期间，控制通道上的输入事件延迟不显著高于无传输时；
6. 传输中途取消，通道关闭，两端缓冲清理，不影响后续剪贴板同步；
7. 多张图片按序传输，序号与总数与元数据一致，无丢失无重复；
8. 隐私屏/锁屏状态下不读取、不发送剪贴板图片；
9. 审计行存在、带 MIME 与字节数，且既不含图片字节也不含缩略图；
10. 文本剪贴板同步不受影响，原有 E2E 全绿。

## 6. 为什么当前停在 fork 外

读桌面剪贴板位图、写桌面剪贴板位图都需要平台 API，位于预编译
`quickdesk_host` 内部。fork 侧的 `clipboard-handler.js` 只能读到浏览器
`navigator.clipboard` 暴露的内容，拿不到 Host 侧的系统剪贴板位图。

因此正确路径是向 `barry-ran/quickdesk-remoting` 提交该协议与实现；
fork 侧可先完成的是 WebClient 的图片读取、写入与审计接线，
并在 Host 未声明能力时明确降级为文本，而不是假装支持。
